    @codeperfect/task-runner

    Task Runner

    A dependency-aware task runner with a compiled CLI and reusable library. Requires Node.js 24 or newer. No consumer-specific integration or runtime TypeScript loader is required. Local development preparation installs a source CLI shim; packed consumers use the compiled executable without running that development-only setup.

    Install

    Install the CLI and library as a development dependency:

    npm install --save-dev @codeperfect/task-runner

    The package provides the task-runner command, a TypeScript library, workspace presets, and a JSON schema.

    Validation

    • npm test runs source-level unit tests.
    • npm run build produces the compiled distribution.
    • npm run docs generates HTML API documentation for the package and presets under docs/api/.
    • npm run e2e tests runtime behavior and isolated consumers. Packaging tests build a temporary copy and skip packing/install lifecycle scripts, so they do not depend on the repository's dist during concurrent validation.
    • npm run validate runs the complete workflow with independent tasks in parallel.
    • npm run validate -- --concurrency 1 runs the complete workflow serially, including build before E2E.

    Configuration

    Put task-runner.json at the repository root:

    {
      "version": 2,
      "defaults": {
        "concurrency": 3,
        "collapse": false,
        "maxTasks": 150,
        "scroll": false
      },
      "packages": {
        ".": {
          "compile": { "run": { "kind": "npm", "script": "compile" } },
          "test": {
            "dependsOn": ["compile"],
            "run": { "kind": "npm", "script": "test" }
          },
          "docs": { "run": { "kind": "npm", "script": "docs", "optional": true } },
          "check": { "dependsOn": ["compile", "test", "docs"] }
        }
      }
    }

    The config is the complete workflow declaration: it lists configured package paths, task names, dependencies, and npm script references. The runner does not discover workspace packages or decide which scripts and task groups belong in the project. The project-maintenance tool or project owner that writes this file owns those decisions.

    The optional defaults object sets runner behavior when the corresponding CLI option is omitted. It accepts ci, concurrency, collapse, maxTasks, and scroll. An explicit CLI option takes precedence over its configured default; otherwise built-in defaults apply. The CI environment variable still enables CI behavior, and an explicitly configured concurrency can override its sequential concurrency default.

    Keep compile and test as ordinary npm scripts; add "check": "task-runner run check" to package.json. Task references are explicit, not inferred from shell text. Use { "kind": "shell", "command": "..." } for an intentional platform-specific shell command. npm tasks accept an args array, forwarded after npm run <script> --, and preserve npm lifecycle hooks.

    npm run check
    npm run check -- --ci
    npm run check -- --concurrency 3
    npm run check -- --collapse false
    npm run check -- --collapse false --max-tasks 150
    npm run check -- --no-scroll --collapse false --max-tasks 1000
    npm run check -- --no-cache

    Package keys are relative paths using /, or . for the root. Each package maps local task names directly to definitions; there is no tasks wrapper or entrypoint mapping. A bare dependency such as compile refers to the same package. Use packages/lib#build for another package or .#build for the root. The # separator is reserved in package paths and task names. Commandless tasks provide groups and aliases; any task is directly invocable. Invoking a command starts at that command without pulling in earlier steps. Groups recursively select the members listed in their dependsOn, stopping at commands. Command dependencies only order tasks already selected. For example, task-runner run mutation and task-runner run mutation:back skip test, including through workspace groups and aliases. Dependencies between selected mutation tasks are still respected. A test:all group that explicitly lists both test and mutation runs test first. Groups must list every intended command: a build pipeline lists clean, compile, and resolve-paths, not just its final step. Generated configuration omits empty dependency lists. Version 1 is not supported. Invoking from a workspace selects that package's task without accidentally selecting a root aggregate. Nested directories select their nearest containing configured package. --config <path> and --package <relative-path> override discovery/selection. Settings such as --concurrency, --ci, --collapse, --max-tasks, and --scroll override matching values in defaults. The schema is exported as @codeperfect/task-runner/schema.json.

    Persistent successful-result cache

    Opt deterministic commands or groups into caching with explicit file inputs:

    {
      "cache": {
        "inputs": [
          "src/**/*",
          "package.json",
          "package-lock.json",
          "tsconfig*.json"
        ],
        "exclude": ["src/generated/**"],
        "env": ["NODE_ENV", "NODE_OPTIONS"]
      },
      "run": { "kind": "npm", "script": "test" }
    }

    Patterns are relative to the configuration root, including for workspace tasks. Include all relevant configuration, dependency sources, and environment names; the runner does not infer them. Groups can also declare outputs, such as ["packages/lib/dist/**/*"], to require intact artifacts before skipping their selected commands. Every output pattern must match a file.

    Successful results persist in .cache/task-runner (add .cache/ to .gitignore). Content changes, added/deleted inputs, command changes, relevant environment or Node/platform changes, and missing/modified outputs invalidate entries. Progress shows cached and the prior success time; JSONL events explain misses. Completed checks remain reusable if another task fails. Artifacts are verified in place, not restored; external side effects must not be cached.

    --no-cache or runTasks("check", { noCache: true }) runs the complete selected plan and refreshes successful records. Direct npm calls bypass the runner and remain unaffected. Cache IO or malformed-record failures are reported; bypass can repair malformed entries through successful execution.

    Library and presets

    import { runTasks } from "@codeperfect/task-runner";
    import { createWorkspacePreset } from "@codeperfect/task-runner/presets";

    const preset = createWorkspacePreset({
      packages: {
        ".": {
          compile: { run: { kind: "npm", script: "compile" } },
          check: { dependsOn: ["compile"] },
        },
      },
    });

    const result = await runTasks("check", {
      cwd: "/path/to/repository",
      signal: abortController.signal,
      onEvent: (event) => console.log(event.status, event.taskId),
    });
    // Write preset to task-runner.json; npm scripts remain in package.json.

    createWorkspacePreset is a convenience-only config constructor. It accepts the complete task definitions chosen by the caller and returns a version-2 object compatible with task-runner.json; it does not inspect the project or decide which packages, scripts, or task groups to include. When a task references an npm script, that script's command remains in the configured package's package.json; the config names the script the runner should execute.

    compileGraph and executeGraph also support an injected command executor for non-process integrations. Library calls return results or propagate boundary errors; they never set process exit status or install global signal handlers.

    Runtime behavior

    • Validate the configuration, task references, and cycles before execution.
    • The runner does not interpret package.json. Declared cache inputs can hash its contents without inspecting scripts. Required npm scripts are attempted through npm and fail as task execution if missing; an optional npm script adds --if-present and succeeds when absent.
    • Execute shared tasks once per invocation, with one global leaf-command limit.
    • Default concurrency is half the available CPUs, rounded down, with a minimum of one. defaults.concurrency or --concurrency N sets a positive integer limit. Non-empty CI, defaults.ci, or --ci defaults to sequential commands and streams output; configured or CLI concurrency takes precedence.
    • On failure, stop admission, block dependents, cancel owned active processes, and wait for cleanup. Windows cancellation terminates the owned tree; POSIX cancellation escalates from SIGTERM to SIGKILL.
    • Interactive terminals show nested groups with animated running tasks, durations, readable package labels, and distinct waiting/ready/success/failure/ blocked/cancelled states. Unstarted and successful groups collapse by default; groups expand when their subtree starts, while nested unstarted groups remain collapsed. Failed, blocked, and cancelled groups stay expanded; defaults.collapse or --collapse true|false sets the collapse behavior; explicit CLI values win. This option does not affect execution or plain CI output.
    • Groups stay pending until work in their displayed subtree starts. Shared dependencies displayed elsewhere do not activate waiting workspaces or later phases such as pack and test:all. Group timers start with their subtree's first work and stop when the group finishes, without summing overlapping durations.
    • Live status icons are colored: cyan running spinner, green success, red failure, yellow ready/blocked, magenta cancelled, and gray pending. Set NO_COLOR or FORCE_COLOR=0 to disable colors without losing state icons.
    • Shared prerequisites appear once. Workspace tasks belong to their matching validation group when it is included; otherwise their first containing group owns the display. Empty cross-package aggregate wrappers are omitted. Display ownership never changes execution order or concurrency.
    • defaults.maxTasks or --max-tasks N sets the interactive task-row cap to a positive integer, default 100, excluding the omitted-task summary. Live redraw fits the terminal viewport; the final listing is preserved in scrollback up to the configured cap. --collapse false retains completed children in the final listing after success, failure, or cancellation, regardless of terminal height.
    • CI, redirected output, and TERM=dumb use concise non-animated progress. Full transitions remain in JSONL. Animation stops before final diagnostics. Rendering uses log-update, not Listr2 or a second task scheduler.
    • Scrolling is enabled by default. defaults.scroll, --no-scroll, or --scroll sets the alternate-screen live view, with explicit CLI values taking precedence. Use Up/Down, Page Up/Down, Home/End, or the mouse wheel where SGR mouse reporting is supported (such as compatible Git Bash terminals). A pinned header shows the command; the footer shows the visible line range. Both disappear when the view closes. npm scripts show npm run <script> with forwarded arguments; direct calls show task-runner and its arguments. Shell quoting is reconstructed, not recovered from shell history. Blank rows separate tasks from the header and footer. The two-line footer shows task counts by status, then the line range/navigation controls. Counts include only unique command tasks throughout the plan, regardless of collapse, scrolling, or the display limit; groups are excluded and zero-count statuses are omitted. Running counts reflect the global command limit, not group spinners, which indicate started work in their displayed subtree. Long headers wrap, bounded to leave task space; tiny terminals omit the header, spacing, or counts as needed. Ctrl+C cancels the run normally. On completion or failure the normal screen/input modes are restored and the final tree is printed into scrollback, with a blank line above and below it. Terminal scrollbars/Shift+wheel are not the live viewport controls. Scrolling activates only with TTY stdin; CI, redirected output, and dumb terminals retain plain output.
    • Logs use logs/task-runner/<pid>/<workspace-task>-<timestamp>.log, with filename-safe names and timestamps. Successful/cancelled output logs are removed after cleanup. Failed commands print a readable task name and relative log path without runner stacks; cancellation adds no error diagnostic. Unexpected runner/cleanup failures still surface normally. After success, failure, or cancellation, a persistent task-status summary follows any failure/log messages, including in plain/CI output. It uses the same command-only counts as the live footer and ends with the completion timestamp in ISO 8601 UTC format (| Finished at: <timestamp>). Structured events remain in separate events-<run-id>.jsonl files per invocation. Command output may contain sensitive tool output; treat retained logs accordingly.
